The rule that scoped this console

docs/design/console-ia.md, the frame docs/design/console-visual.md, the apparatus

The console is a disposition surface: a place to decide and to act. It is never a place to read. Every screen either resolves something into a new state, or shows the consequence of a policy so a decision about it can be made. Nothing exists to be browsed.

That single rule does the scoping. It kills the file browser, the tag manager, the timeline visualisation and the dashboard, all of which would otherwise arrive by reflex. Reading belongs to the Obsidian mirror, which is better at it and works offline. Authoring and bulk work belong to the CLI. The console never grows a compose box: every write it performs answers a fact already on screen.

Agree or disagree with that rule first. Everything below follows from it, and if it is wrong then eight of the ten screens here are wrong.

Where this preview filled a gap the design left

  • Fonts. The design names Source Serif 4 for fact prose and Iosevka Fixed for everything else, self-hosted, two woff2 files. This file makes no network request, so prose falls back to Charter or Georgia and chrome falls back to the system mono. Iosevka's 0.5em advance is the whole density argument in section 2 and none of it is visible here, so the client column is set at 17ch rather than the specified 14ch to stop a name wrapping in the fallback. Judge the structure, not the letterforms.
  • The empty grant cell. The visual pass draws it as an em dash. House style bans that character, so this preview prints a middle dot and keeps emptiness as the signal.
  • Row counts. Compact is specified at 24px and 33 rows on a 1440 by 900 display. These mockups show six to twelve rows each so a screen fits on one page next to its notes. The density claim is untested here.
  • Keyboard. The design specifies two dispatchers, a command palette and about twenty verbs. This preview binds screen movement only: number keys, g chords, arrows. Verbs are printed where they belong and do nothing.
  • Motion. The design's default is that nothing moves, and nothing moves here. The 600ms hold-to-confirm delete gate is drawn as a static state rather than run.
Both design passes recommend holding the build. Their words: four of the five ranked jobs depend on the sensitivity axis and per-client grants, and an admin UI built early against a store of two hundred facts and one client is a screen with nothing to do. Since they were written, Phases 2 through 4 landed in the tree and none of it has been verified against a live server. Nothing is deployed, no OAuth flow has completed, and no private row has been encrypted and read back. The console would be the first thing to read a store that has not yet proved it can hold anything.

The authority column is the honest part, and it inverts what the design assumed. The design README asks for grants to move from AUTH_TOKENS into a versioned Postgres table in Phase 3. Decision 0003 refused half of that on purpose: authority follows the credential. A token from AUTH_TOKENS carries its grant there, a client id this server issued carries its grant in its row, and no code path copies one into the other. The record's reason is that a seeded copy has two quiet failure modes and both end with the file and the row disagreeing about what a client may see.

The consequence for this screen: the editable authority is the less expressive one. An OAuth client's grant is one of three fixed profiles, full, standard and narrow, assigned at the consent screen, where read and write are the same namespace set at every profile and only full carries sealed, deletes or registry writes. The expressive authority is the environment: AUTH_TOKENS takes per-namespace ceilings on read and write independently. That one needs a restart to change and the console must never write it, because a console that could rewrite it would put the server in charge of its own access control.

So the row for claude-code-mac is read-only by design, the row for chatgpt is editable in principle and has no editor, and the console's own lumberroom-ui grant, read everywhere up to sealed with no writes and no sealed decryption, is not expressible as any profile the server ships.
Unresolved between the two design passes. The IA demotes instrumentation from a section to two lines on this screen, on the argument that adjacency is what the browser adds: the counts sitting directly beneath the grant they belong to is one thought. 2. Editing a grant ceiling per namespace, now that there are two axes

verdict: belongs, and the console cannot have it until the grant model grows

The design assumed clauses with a ceiling each and built the blast radius on top of them. The server enforces exactly that model and only AUTH_TOKENS can express it. An OAuth client gets one of three profiles with read and write identical. So the editor on the Policy screen is drawn against a grant model that exists in the enforcement path and not in the authoring path.

What has to happen first: set_client_grant already takes clause lists rather than a profile, so the store is ready. What is missing is a route that calls it outside a consent flow, a way to say per-clause ceilings at that route, and a decision about whether profiles stay as presets on top of clauses or go away.

Shown on the Policy screen, marked.

3. The classification table as an editable surface

verdict: belongs, read-only for now, and it is not urgent

This table decides what is private, so it decides what gets encrypted, and the PRD's named failure condition is everything ending up in open because classifying is a chore. An interface that shows a namespace holding three facts at open next to a rule that classifies its neighbour private is doing the console's job.

Two facts make editing dishonest today. The rules resolve once, at boot, beside the key check, so a change made in a browser does nothing until a restart. And when SENSITIVITY_DEFAULTS carries rules the table has no say at all, which is the state every compose deployment ships in. A console that wrote rows into a table the server ignores would be worse than no editor. Show the rules, name the authority, print the caveat.

Shown on the Policy screen, read-only, marked.

4. Key state, and the fact that a mismatch leaves private writes refused

verdict: belongs as a band and one status line, not as a screen

A key mismatch is the failure this system is worst at showing. Every open read and write keeps working, the server reports itself healthy, and every private write is refused. The one thing that catches it today is a line in the boot log and a boolean on /readyz. The Inbox already answers "is this thing working" when the queue is empty, and this is the answer it would otherwise get wrong.

Escrow is the harder half and the console cannot resolve it. Decision 0004 leaves it open and says to answer it before turning on encryption for writes that matter. A console that offers a private write while escrow is undecided is helping the owner strand data.

Shown as a band on the Inbox and a block on the Policy screen.

5. Sealed items, which the server cannot read and can only count

verdict: no screen. A row state and an inventory line

Sealed content has no plaintext to show, no search to run and no ordering worth browsing. It is retrievable by exact key only, and the server cannot enumerate the names because the key is an HMAC computed on the client. A count per namespace is the whole honest surface.

What the console does not do

IA: what not to build each of these would otherwise arrive by reflex

resolvesWhere the console stops. A reader should finish knowing the boundary.

refused by the scoping rule

  • A browse-all table of every fact with filters and pagination. The single most likely thing to be built and the most useless.
  • A compose box. Break that and the console becomes a second-rate note app. Every write it performs answers a fact already on screen.
  • A graph view. Supersession chains are linear by construction, because a supersede whose target is already superseded is refused. Branching is defined as an error, so the only structure a graph would add is the one that cannot exist.
  • A stats page, in the IA's reading. Two lines on Clients instead.
  • A timeline. The value strip carries intervals, which is what a decision log is for. A list of write timestamps is an audit trail and tool_calls already is one.
  • A dashboard. The Inbox's empty state is the health readout.

refused because it belongs elsewhere

  • A registry CRUD form.
  • A tag manager.
  • A namespace management screen. Namespaces are created by writing to them.
  • An export or backup UI. The CLI owns export, backup, doctor and eval.
  • A settings screen. Configuration is environment variables on a box the owner owns, and a settings screen would be a lie about where the truth lives.
  • A theme toggle. The light theme exists and the switch is not a product feature. This preview carries one because it has to be judged in both.

refused as noise

  • Onboarding, tours, tooltips explaining what a namespace is, empty state illustrations.
  • A word-level diff of two one-sentence facts.
  • Notifications and weekly digests. The Inbox count is the notification.
  • Group actions as checkbox selection. They exist as a rule with a dry run.

refused as scope

  • Websockets and any live tail. The new-row tick is specified and not scheduled, because nothing in the repo carries a transport for it.
  • Anything multi-user. There are no user accounts, only one owner, and no sign-up path that could make a second.
  • A conversation viewer, which would mean storing transcripts.
  • React, Tailwind, an icon library, a CDN font, a service worker, client-side routing, analytics of any kind. Server-rendered HTML, one stylesheet, about 300 lines of vanilla TypeScript, two self-hosted font files, under 90KB to the client.

Mobile

One job fully, one at a glance, nothing else. The panic delete is the strongest mobile argument in the product: the realisation that something sensitive got stored does not wait for a laptop, and the surfaces most likely to have stored it are on the same phone. Keep the health strip, the Inbox read-only, search with the client selector, the fact panel and delete. Drop grant editing entirely, because a fat-fingered ceiling change is exactly the mistake this system exists to prevent and it is never urgent.

The job the design is suspicious of

"What did I used to believe", the decision log. The supersession chain is a side effect and exactly the kind of thing a builder over-invests in. It gets a widget, which is the value strip in the fact panel, and never a screen.

Design documents: docs/design/console-ia.md, docs/design/console-visual.md, docs/design/README.md. This preview shows what they specify and marks what the system cannot yet answer. It builds nothing.
